# Phase 54: Cross-Library Component Assembly and PowerPoint Compatibility — Implementation Plan

## Outcome

Replace fixed-reference replay with an agent-directed but compiler-governed
design workflow. The agent receives only a client brief, facts and approved
assets. It derives a defensible page count and narrative, retrieves a small
certified visual shortlist, selects physical page/component IDs, and produces
an editable PPTX that visibly renders in real PowerPoint.

The existing 15-page `工作总结.pptx` is retained only as a same-source technical
regression. It cannot satisfy this phase's acceptance by itself.

## Work Package 1 — Seal the PowerPoint Regression

1. Keep a frozen source-native fixture that opens visibly in PowerPoint,
   including the `custDataLst/tags` regression slides and a chart slide.
2. Extend recursive OPC verification to inspect every relationship-bearing XML
   attribute (`r:id`, `r:embed`, `r:link`), not just `.rels` targets.
3. Maintain a discard-policy registry. Each discarded relationship class has a
   sanitizer for its referring XML or causes a hard reject.
4. Add test cases for tags metadata, chart/workbook/style closure, absent
   layout/master targets, unsafe external targets and a PowerPoint rendering
   fixture.
5. Record exact SHA, importer version and PowerPoint evidence. LibreOffice
   evidence is supplementary only.

**Done when:** no fixture can leave a dangling owner reference; the exact
artifact is visible/editable in PowerPoint and all portable checks still pass.

## Work Package 2 — Make Narrative and Page Count First-Class

1. Add a versioned `brief.normalized.json` schema with audience, purpose,
   delivery setting, facts, evidence, approved assets, constraints, unknowns
   and safe defaults.
2. Add a versioned `narrative-plan.json` schema. A beat has a business
   question, audience decision, key message, facts, desired grammar, density,
   priority and explicit merge/split/delete decision.
3. Build deterministic plan validation:
   - no page without `page_intent` and `key_message`;
   - no under-filled beat unless it is cover/section/closing;
   - no over-capacity beat without a split decision;
   - every section divider has associated evidence within two pages;
   - all supplied material is assigned, intentionally deferred, or rejected
     with a reason.
4. Make final slide count equal validated delivery beats, not a prompt
   parameter. The agent may state a range during planning, but compilation
   serializes a single justified count after validation.

**Done when:** a client pack with no requested count produces a stable
page-rationale ledger and rejects the former “section → title → no content”
pattern.

## Work Package 3 — Index and Retrieve Visual Material Hierarchically

1. Keep private assets outside Git and the client folder. Bind each page
   observation to its rendered image SHA and source package/page lineage.
2. Store deck-level family/palette/tone/industry/density, page-level
   role/grammar/capacity, and component-level intent/member set/relative
   placement/allowed and prohibited adaptations.
3. Compile the final `certified-core` disposition as a hash-bound overlay.
   Validate full package SHA, slide number and rendered visual SHA; block every
   matching final `deny` page in materialization metadata. Runtime must reject
   a stale overlay, and catalog maintenance must run through the manager rather
   than hand-edited JSON.
4. Build deterministic query modes:
   - `anchor`: select a dominant style family from brief and audience;
   - `page`: return at most three whole-page candidates for a delivery beat;
   - `component`: return at most three compatible certified regions only after
     a whole-page candidate cannot express the beat;
   - `exact-replay`: regression-only mode, explicitly marked non-production.
5. Return IDs, safe summaries, capacities, compatibility and rationale—not raw
   private paths or an unbounded preview gallery.

**Done when:** same query returns identical ranking, rejected candidates are
explainable, and selection does not require scanning private folders.

## Work Package 4 — Constrain the Agent's Design Decisions

1. Agent workflow: clarify missing client requirements → normalize brief →
   draft narrative → validate page count → choose anchor → retrieve candidates
   → emit selection plan → compile → inspect/repair → release.
2. The selection plan may contain only template/component/fact/asset IDs and
   declared slot operations. It cannot contain coordinates, RGB values, fonts,
   arbitrary shapes, OOXML, code or a release score.
3. Lock one dominant style family. Permit an explicitly catalogued compatible
   fallback only when no anchor candidate meets content capacity.
4. Enforce for a substantive 10+ page result: at least 6 source packages, 5 approved
   categories, no package contributing over 4 full pages. This proves assembly
   without forcing a visually incoherent or media-heavy source count. Components
   have separate provenance and cannot obscure page-source lineage.
5. The compiler owns slot-safe typography, reflow and styling. Long copy is
   shortened, split or replaced with a certified density-safe alternative;
   shrinking below the design minimum is prohibited.

**Done when:** the agent can make bounded design choices but cannot silently
become a freeform drawing engine.

## Work Package 5 — Assemble, Repair and Explain

1. Implement whole-page and component closure import with full OPC dependency
   traversal. Preserve editable native text, shapes, charts, tables, media and
   themes; reject macro/OLE/script/file relations.
2. Persist versioned `selection-plan.json` and `assembly-report.json` with
   catalog/observation/preflight/adapter/compiler digests, source IDs, slot
   changes, fallback decisions and complete lineage.
3. Replay only with the pinned compatible compiler. A digest mismatch emits a
   stable migration report and fails closed; it never reinterprets old component
   keys.
4. Apply repairs in order: remove/merge empty beats → rewrite/split long copy
   → choose higher-capacity page → split evidence → adjust declared safe slots.
   Do not add decorative filler to conceal missing content.

**Done when:** an artifact replays byte-stably with matching versions, or gives
a precise non-destructive migration report.

## Work Package 6 — Acceptance Harness and New Case

1. Create a clean `某市中心医院 2026 年财务运营数智化升级项目立项汇报`
   folder containing only client requirements, business facts and approved
   assets. It contains neither a reference PPTX nor a requested page count.
2. Run `gpt-5.6-terra` medium through the installed Skill using the staged
   workflow. Preserve transcript and all plan artifacts.
3. Require package validity, relationship closure, source protection,
   editability, overflow/overlap/density/style/lineage checks and real
   PowerPoint open/render evidence for the final exact SHA.
4. Run three fresh anonymous visual reviews from independent contexts. The
   author cannot score or release its own deck.
5. Publish only clean requirements, schemas, evidence hashes and redacted
   reports. Keep private PPTX files, previews and commercial material ignored.
6. After the professional report passes, create an independent clean academic
   defense pack with complete research facts and no reference PPTX. Run the
   same narrative-derived count, style planner, native binding, PowerPoint and
   three-context blind-review gates; do not reuse the report's narrative or
   composition plan.

**Done when:** both professional-report and academic-defense artifacts pass all
Phase 54 requirements; otherwise record the exact
failed gate and iterate without declaring release.

## Execution Order

1. Work Package 1 and the schemas in Work Package 2.
2. Narrative validator and controlled agent instructions.
3. Hierarchical library query/index migration.
4. Versioned selection/assembly contracts and importer hardening.
5. Acceptance harness and clean dynamic-count case.
6. Independent PowerPoint + blind-review gates, audit, then release decision.
