# Phase 27.1 Specification: Huashu Design Reference Assimilation

**Status:** Locked
**Amended:** 2026-07-21 by the accepted Phase 27.2 architecture
**Risk:** high
**User-facing:** yes
**Requirements:** 6

> **Supersession note (2026-07-21):** This specification preserves the Phase 27.1 implementation and evidence boundary. The later user decision keeps DeckPlan and RenderPlan canonical but replaces the governed daily COM renderer with a portable PptxGenJS + OOXML + LibreOffice path in Phase 27.2. COM remains an explicit legacy backend and sampled release certifier. Historical PASS, PARTIAL, and NOT_RUN evidence below is not rewritten.

## Goal

Move narrative, art direction, layout choice, brand consistency, and visual-quality judgment from model improvisation into strict, deterministic, testable Skill capabilities while preserving native editable PowerPoint output.

## Background

Phases 22-27 created a reliable Windows-native compiler and delivery gate, but the model still owns too much story construction and visual direction. Ordinary-model benchmark attempts show schema near-misses, incomplete narratives, repeated forms, and weak art direction. Huashu offers useful design-process ideas, but its HTML conversion engine and prompt-only style catalog do not meet the native editability and transaction contract of this Skill.

## Requirements

### V5-REF-01: Reproducible Source and License Boundary

**Current:** Huashu was inspected from a temporary clone, while the active Skill has no committed source pin, review inventory, or license notice.
**Target:** Freeze the upstream URL, full commit, archive/tree/LICENSE hashes, reviewed paths, MIT notice, and per-item accept/adapt/reject decisions; copy no runtime, style prose, or media.
**Acceptance:** A verifier can reproduce all hashes, find the MIT notice, and map every adopted principle to independently authored code or documentation.

### V5-REF-02: Immutable Fact and Narrative Authority Chain

**Current:** DeckPlan is strict, but content-only planning maps supplied blocks directly to slides and does not guarantee fact-backed story beats.
**Target:** Implement trusted sources to immutable FactStore v1 to strict BriefPlan v1 to deterministic NarrativePlan v1 to canonical DeckPlan v1, with direct DeckPlan compatibility explicitly marked when fact governance is unavailable.
**Acceptance:** Strict schemas and tests reject unknown facts, conflicts, invented text/numbers, raw design, unsafe normalization, and missing critical evidence while preserving existing DeckPlan tests.

### V5-REF-03: Native Art Direction, Brand, and Layout System

**Current:** Eight themes and 72 layout IDs exist, but direction choice is implicit, variants are insufficiently differentiated, and brand/asset availability weakly influences layout choice.
**Target:** Add twelve neutral art directions, three deterministic candidates, two-page native proofs, BrandSpec, font inventory, geometry signatures, weighted layout scoring, semantic-form authority, and asset-safe fallback.
**Acceptance:** Registry, selector, proof, layout, brand, font, chart, and asset tests prove determinism, structural variation, native editability, fail-closed incompatibility, and no placeholder promotion.

### V5-REF-04: Quality Report v2 and Two-Stage Repair

**Current:** Quality v1 covers five rendered layers and up to two structural passes, but it lacks narrative/compiler namespaces and pre-render story/design replan.
**Target:** Merge input, narrative, compile, render, preview, package, and editability findings; allow at most one pre-render replan and one post-render repair, with immutable facts and snapshot rollback.
**Acceptance:** Tests prove stable dedupe/order, hard-gate precedence, strict lexicographic improvement, rollback on exceptions or regressions, and no mutation of facts, numbers, citations, user text, source, or final output.

### V5-REF-05: Weak-Model Skill Workflow

**Current:** Weak-model guidance is mainly prose and model outputs fail on harmless version, alias, slug, wrapping, and schema mistakes.
**Target:** Add one bounded deterministic normalization pass, structured errors, at most two model retries, safe defaults, progressive Skill references, and behavioral Skill TDD.
**Acceptance:** Same-prompt baseline/with-skill tests reduce schema/planning failures, raw-design fields remain rejected, and unrelated typo/edit tasks do not trigger full design-direction work.

### V5-REF-06: Calibration and Complete Fingerprints

**Current:** Phase 28 evidence is partial, dirty, pre-Huashu, and lacks complete engine/environment fingerprints.
**Target:** Freeze six independent calibration cases and require canonical hashes for engine, renderer, verifier, registries, schemas, Skill, corpus, protocol, prompts, thresholds, dependencies, provider/model, OS/locale, fonts, and assets. A PowerPoint fingerprint is mandatory only for PowerPoint-certification evidence.
**Acceptance:** Same-input before/after packets are reproducible, pre-Huashu and mixed renderer/verifier fingerprints are rejected, PowerPoint certification cannot omit its PowerPoint fingerprint, and the formal 180-trial protocol cannot aggregate dirty or unavailable evidence as success.

## Boundaries

### In Scope

- Strict model-facing and internal schemas, deterministic planners, registries, selectors, traces, QA, repair, Skill documentation, calibration, and benchmark refreeze.
- Native PowerPoint text, shapes, charts, tables, diagrams, images, notes, links, export, package validation, and edit sentinels.
- Independently rewritten Huashu-inspired principles and an MIT attribution record.

### Out Of Scope

- Huashu HTML-to-PPTX runtime, copied prompts/styles/showcases/media/fonts, arbitrary layout DSL, arbitrary code/macros/plugins, hosted gallery, automatic image-generation promises, PPT/PPTM delivery, and claims of senior-designer equivalence before Phase 28/29 evidence.

## Constraints

- DeckPlan v1 raw-design rejection and source/output transaction safety cannot weaken.
- FactStore content, numbers, units, citations, language, and source locators are immutable.
- All model-controlled objects use `additionalProperties: false` and registered enums/IDs.
- New visuals must remain native-editable where the existing renderer promises editability.
- Existing user files and pre-Huashu evidence are preserved but excluded from formal aggregation.
- Missing provider or Windows evidence is `NOT_RUN`/failed, never imputed.

## Decision Log
