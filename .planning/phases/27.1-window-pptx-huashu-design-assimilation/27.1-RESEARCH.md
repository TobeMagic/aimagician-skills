# Phase 27.1 Research: Current Gaps and Huashu Assimilation

> **Supersession note (2026-07-21):** This research correctly rejected importing Huashu's HTML runtime and records the then-current COM production recommendation. Phase 27.2 later preserves the clean-room/HTML rejection but supersedes COM as the governed daily renderer with direct RenderPlan-to-PptxGenJS generation and independent LibreOffice proof.

## Objective

Determine which design-planning ideas materially raise weak-model PPTX quality, which current native-engine gaps they address, and how to implement them without importing a second rendering engine or weakening safety boundaries.

## Local Evidence

The local evidence is the current source, registries, schemas, tests, Phase 22-28 planning artifacts, dirty-tree manifest, benchmark run summaries, and native Windows evidence already recorded in the repository.

### Current Engine

The current Skill already has a strict DeckPlan boundary, 15 archetypes, semantic page ranking, capacity splitting, eight themes, 24 page families, 72 variant IDs, native editable charts/tables/diagrams, transactional saves, five-layer QA, and bounded candidate repair.

The main remaining gaps are upstream of COM and inside visual decision quality: narrative completeness is model-owned; the content-only route maps one block to one slide without constructing a story; layout variants collapse into too few geometry grammars; theme tokens are only partly consumed; asset absence creates weak placeholders; QA is stronger on conformance than concept, hierarchy, image crop, natural line breaks, and cross-page visual rhythm.

Ordinary-model benchmark evidence confirms schema near-misses, invalid IDs, unsupported fields, scenario aliases, malformed JSON, missing facts, and weak story coverage. The current benchmark runs are incomplete and cannot support a before/after claim.

## Accept / Adapt / Reject

Accept the principles of three real directions, two-page grammar proofs for decks of five or more slides, brand/product assets before palette, one action claim per page, content-derived visual motifs, anti-AI-slop rules, and concept/content fit before surface polish.

Adapt these into neutral native-PPTX art-direction registries, strict BrandSpec and asset manifests, deterministic safe/editorial/expressive candidates, direction decision traces, installed-font discovery, rule-based QA, and calibration benchmarks.

Reject HTML-first conversion, seconds-based randomness, mandatory human pauses for unattended work, copied named styles/showcases/media, partial deck delivery, placeholder imagery, and long prompt-only gates.

## Options

1. Replace the native renderer with Huashu HTML conversion: rejected because it loses native object coverage, transaction guarantees, and PowerPoint-native QA.
2. Copy Huashu prompts and style prose into the existing Skill: rejected because prose gates remain model-dependent and create licensing and consistency risk.
3. Independently implement the useful principles as strict schemas, registries, selectors, native proofs, and QA rules: selected.

## Recommendation

Keep DeckPlan v1 and the Windows COM renderer as the production core. Add a smaller model-facing BriefPlan backed by immutable facts, deterministic narrative planning, neutral art directions, brand/asset requirements, layout scoring, QA v2, two-stage repair, and same-input calibration evidence.
