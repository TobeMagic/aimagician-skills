# Phase 27.2 Discussion Log

**Status:** Decisions locked
**Date:** 2026-07-21

## Trigger

The user asked why PowerPoint COM failed with `TYPE_E_CANTLOADLIBRARY`, whether COM was necessary or complete, whether HTML or another library could replace it, and which blockers remained. The user then approved implementation of the portable-first plan.

## Evidence Discussed

- Office, Windows Python, and pywin32 are all x64.
- PowerPoint's ProgID/CLSID, executable, Microsoft TypeLib, and `MSPPT.OLB` are valid and loadable.
- Early-bound `DispatchEx` fails at `_Application.QueryInterface`.
- `_Application` interface registration points to a stale WPS TypeLib and a missing `wppapi.dll`.
- Late-bound `dynamic.Dispatch` and explicit `CoCreateInstance(..., IID_IDispatch)` work and quit without residue.
- PptxGenJS 4.0.1 provides native editable core PowerPoint objects but not animation, SmartArt, native grouping, or existing-deck import.
- PptxGenJS's official HTML conversion targets HTML tables, not arbitrary slide DOM.
- A local spike proved PptxGenJS output differs only in core and ZIP timestamps before normalization.
- LibreOffice is not PowerPoint-equivalent but can provide an independent open/export proof renderer.

## Decisions

1. Use a hybrid architecture, but remove COM from governed daily delivery.
2. Use PptxGenJS as the primary portable generator.
3. Use LibreOffice Headless in WSL as the daily second renderer.
4. Use HTML only for preview and QA.
5. Use PowerPoint only for release sampling and high-risk certification.
6. Keep safe system diagnosis and manual Office/WPS repair guidance; do not mutate the registry automatically.
7. Keep the formal two-model, 180-trial benchmark and human blind review rather than lowering the contract.

## Assumptions

- The repository's strict FactStore-to-RenderPlan authority chain remains the source of truth.
- PptxGenJS 4.0.1 remains available under an acceptable license and the installed Node runtime can execute it.
- LibreOffice differences are evidence to inspect, not permission to alter the canonical PPTX through a round trip.
- Missing provider or PowerPoint evidence remains `NOT_RUN`, never an inferred PASS.

## Rejected Options

- **COM-only production:** rejected because it keeps daily delivery coupled to desktop automation and the current registry state.
- **Arbitrary HTML-to-PPTX as canonical:** rejected because screenshot conversion loses editability and DOM-to-native conversion would create another complex renderer.
- **Marp/image-slide production:** rejected for editable customer deliverables.
- **Aspose.Slides:** deferred as a paid fallback POC only if cross-engine evidence shows LibreOffice is insufficient.
- **Automatic WPS registry cleanup:** rejected as unsafe and unnecessary for portable delivery.
- **Pixel-identical LibreOffice/PowerPoint requirement:** rejected; certification uses open/export/page/quality/repair-prompt gates and records renderer differences.

## Deferred Work

- Aspose.Slides paid POC unless LibreOffice proves insufficient through measured cross-engine failures.
- Automatic Office/WPS repair and registry mutation.
- Full two-model benchmark, human blind review, and frozen PowerPoint certification sampling, which remain Phases 28-29 work.

## Superseded Earlier Assumptions

- The Windows-native renderer is no longer the canonical production renderer; DeckPlan and RenderPlan are canonical.
- Real PowerPoint proof no longer blocks daily customer delivery or Phase 27.2.
- Fake-COM artifacts no longer count as `full-v5` delivery evidence.
- A PowerPoint fingerprint is required only for PowerPoint-certification evidence.
- The earlier statement that the Microsoft type library cannot load is corrected to stale WPS interface registration breaking early binding.
- The completed DeepSeek research session is not the final post-implementation audit and does not replace the second benchmark model.
