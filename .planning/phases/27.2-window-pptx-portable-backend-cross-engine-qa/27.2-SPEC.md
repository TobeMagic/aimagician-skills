# Phase 27.2 Specification: Portable PptxGenJS Backend and Cross-Engine QA

**Status:** Locked
**Risk:** high
**User-facing:** yes
**Requirements:** 9

## Goal

Remove PowerPoint COM from the governed daily-delivery critical path while preserving deterministic planning, native-editable PPTX output, transactional safety, and fail-closed customer quality gates. Keep PowerPoint as an explicit legacy backend and a sampled, read-only release certifier.

## Background

Phases 22-27.1 produced a strict FactStore-to-RenderPlan authority chain, governed design system, COM renderer, Quality-v2, bounded repair, and reproducible benchmark contract. Real Phase 27.1 delivery proof was blocked when early-bound pywin32 failed with `TYPE_E_CANTLOADLIBRARY`.

Diagnosis later proved that Microsoft PowerPoint itself is usable: `MSPPT.OLB`, `LoadTypeLib`, `LoadRegTypeLib`, and late-bound `IDispatch` work. The `_Application` interface registration instead points to a stale WPS TypeLib whose `wppapi.dll` no longer exists. This makes early-bound COM unreliable on the current host but does not justify keeping COM as a mandatory production dependency.

The user selected PptxGenJS 4.0.1 as the governed renderer, LibreOffice Impress plus Poppler as the independent daily proof renderer, HTML as proof/QA only, and PowerPoint as sampled certification. The canonical authority remains FactStore, BriefPlan, NarrativePlan, DeckPlan, and RenderPlan.

## Requirements

### V5-PORT-01: Backend-Neutral Execution and Capability Negotiation

**Current:** The runner, transaction, and delivery checks assume that the production renderer and reopened-candidate inspector are COM-backed.

**Target:** Introduce a backend-neutral RenderPlan execution contract and explicit capability manifest. Governed `--backend auto` selects PptxGenJS without COM. Required unsupported capabilities fail before candidate creation or process mutation; no route silently falls back to COM or a raster slide.

**Acceptance:** On a host where COM dispatch is denied, `--backend auto --verification portable` completes without starting PowerPoint and records PptxGenJS as the selected backend. Required animation, SmartArt, physical-template import, macro-enabled output, or native grouping fails pre-mutation with a stable capability error. Explicit compatible legacy routes may still select COM.

### V5-PORT-02: Native Editable PptxGenJS Object Coverage

**Current:** Native-object proof is bound to COM or Recording-COM, and PptxGenJS is not installed or integrated.

**Target:** PptxGenJS 4.0.1 directly maps registered RenderPlan items to native editable text, shapes, images, tables, charts, six diagram families, notes, hyperlinks, masters, and footers. Portable diagrams remain editable child shapes with stable logical-group metadata. Each object carries a stable `objectName` and structured `altText` identity.

**Acceptance:** Positive fixtures across 16:9, 4:3, and custom page sizes contain the expected OOXML object types, text, data, notes, links, identity values, z-order, and page geometry. No governed slide is promoted as a full-slide screenshot. Portable output does not claim unsupported PowerPoint-native grouping or motion.

### V5-PORT-03: Deterministic Package and Transaction Safety

**Current:** A PptxGenJS spike showed identical decks differ in core-property and ZIP timestamps, so raw output is not byte-deterministic.

**Target:** Normalize core timestamps, ZIP entry order, entry timestamps, permissions, and compression parameters before validation. Preserve candidate-only mutation, source hashes, format guards, and atomic promotion.

**Acceptance:** Two runs from an identical RenderPlan and identical dependency/font/environment fingerprint produce byte-identical PPTX files and identical SHA-256 values. The package opens as ZIP/OOXML, the source hash is unchanged, and no failed candidate is promoted.

### V5-PORT-04: RenderPlan-Aware OOXML Semantic Hard Gate

**Current:** Package validation exists, but the reopened semantic and editability inspection relies on PowerPoint.

**Target:** Add a Python OOXML inspector that resolves content types and relationships, then verifies page count and size, object identities and text, image media and crop, charts and embedded data, tables, notes, links, masters, and relationship integrity against RenderPlan and backend results.

**Acceptance:** Positive fixtures pass. Negative fixtures for a broken relationship, missing Content Type, identity/text mismatch, missing chart workbook, invalid image relationship, malformed note/link, duplicate relationship ID, or unexpected slide size fail before promotion with deterministic finding codes.

### V5-PORT-05: Isolated LibreOffice and Poppler Proof Rendering

**Current:** Real PDF/PNG exports and preview gates require PowerPoint; LibreOffice is not installed.

**Target:** Install and fingerprint WSL LibreOffice Impress. For each run, use an isolated temporary UserInstallation profile and a candidate copy, export PDF headlessly, convert it to PNG with Poppler, and feed those real PNGs to Quality-v2. Never resave the canonical PPTX through LibreOffice.

**Acceptance:** Chinese/space paths and all supported page ratios produce readable PDF/PNG with exact page-count and expected aspect-ratio evidence. Missing executable, timeout, conversion error, missing page, or unreadable PNG fails closed. The candidate PPTX hash is identical before and after rendering, temporary profiles are removed, and no LibreOffice process remains.

### V5-PORT-06: Proof-Only HTML Boundary

**Current:** Phase 27.1 rejects imported HTML-to-PPTX runtimes, but HTML has no positive governed role.

**Target:** Permit only deterministic RenderPlan-derived HTML proof pages using governed design tokens for preview, debugging, and early QA. Model-authored arbitrary HTML/CSS and HTML as the canonical PPTX intermediate remain forbidden.

**Acceptance:** Disabling or failing HTML proof generation does not change the PPTX bytes or portable delivery result. The same RenderPlan produces the same proof DOM. No Huashu runtime, restricted html2pptx implementation, copied prompt/style catalog, or model-authored layout code enters the package.

### V5-PORT-07: Safe Optional PowerPoint Doctor and Certification

**Current:** Early-bound pywin32 fails on this host, current diagnostics overstate the failure as PowerPoint/type-library activation failure, and certification is coupled to generation.

**Target:** Add doctor evidence for Office bitness/version, Microsoft and interface TypeLib registrations, early/late binding, WPS contamination, and process ownership. Certification opens an already-passed portable candidate read-only with macros disabled, exports proof, reports compatibility, and never saves the presentation. It never mutates the registry automatically.

**Acceptance:** The contaminated host is diagnosed as stale WPS `_Application` registration while Microsoft `MSPPT.OLB` and late binding remain usable. With no pre-existing PowerPoint process, an owned late-bound session may certify and quit cleanly. With any unprovable pre-existing process, certification fails closed and terminates nothing. Portable verification can pass while certification is `NOT_RUN`.

### V5-PORT-08: Public Options, Reports, Fingerprints, and Compatibility

**Current:** There is no stable public backend/verification contract, and fingerprints assume PowerPoint is mandatory.

**Target:** Add `--backend auto|pptxgenjs|com` and `--verification portable|powerpoint`, backend capability/result evidence, and staged verification results. Fingerprint Node, PptxGenJS, LibreOffice, Poppler, OS, locale, and fonts; require PowerPoint fingerprints only for PowerPoint-certification evidence. Preserve legacy report readers and explicit COM-only routes.

**Acceptance:** Defaults are `auto` and `portable`; `powerpoint` runs only after portable PASS. Invalid combinations fail with stable errors. Legacy/PPTM/POTM/template-import routes remain explicit and do not bypass v5 gates. Old report readers pass regression tests, and missing or mixed required component fingerprints cannot aggregate into release evidence.

### V5-PORT-09: Real Portable Calibration and Regression Evidence

**Current:** Six calibration cases have deterministic planning and Recording-COM evidence but no real portable PPTX/PDF/PNG proof.

**Target:** Re-run all six calibration scenarios through the real portable backend and stage PPTX, PDF, page PNG, contact sheet, OOXML report, Quality-v2 report, repair log, manifest, and hashes.

**Acceptance:** Every scenario passes package, OOXML semantic, LibreOffice, and Quality-v2 hard gates and collectively covers text, image, table, chart, diagram, notes, links, and all supported ratios. Fault injection proves fail-closed behavior. Historical 505 tests plus all new Node/Python tests pass. PowerPoint is not required for Phase 27.2 PASS and remains a Phase 29 sampled gate.

## Boundaries

### In Scope

- Backend-neutral execution and capability reporting.
- PptxGenJS native editable PPTX generation and deterministic package normalization.
- Python OOXML semantic inspection.
- WSL LibreOffice/Poppler proof rendering and Quality-v2 integration.
- Deterministic proof-only HTML.
- Safe PowerPoint doctor and read-only certification adapter.
- Public CLI/report/fingerprint updates, six real calibration packets, documentation, and tests.

### Out Of Scope

- Arbitrary HTML-to-PPTX conversion or copied Huashu/restricted runtime code.
- Claiming LibreOffice is pixel-equivalent to PowerPoint.
- Automatic registry editing, WPS cleanup, Office repair, or termination of user processes.
- Portable animation, SmartArt, physical template import, macro-enabled output, or native group objects.
- Replacing the 180-trial Phase 28 benchmark, blind human review, or Phase 29 sampled PowerPoint certification.
- Claiming senior-designer equivalence before Phase 28/29 evidence.

## Constraints

- FactStore content, DeckPlan raw-design rejection, RenderPlan registry binding, source/output safety, and bounded repair cannot weaken.
- The model cannot emit executable PptxGenJS, OOXML, HTML, CSS, JavaScript, COM, or layout-coordinate code.
- PptxGenJS is pinned to 4.0.1. Actual Node, LibreOffice, Poppler, OS, locale, and font versions are recorded rather than assumed.
- LibreOffice uses one isolated profile per run and never round-trips the canonical PPTX.
- PowerPoint certification never changes the canonical portable file and is not a Phase 27.2 completion dependency.
- Missing external evidence is `NOT_RUN` or FAIL, never imputed.

## Decision Log

- Continue v5.0 and insert decimal Phase 27.2; do not create a competing milestone.
- DeckPlan and RenderPlan remain canonical and backend-neutral.
- PptxGenJS 4.0.1 is the governed daily renderer.
- LibreOffice Impress in WSL plus Poppler is the independent daily proof renderer.
- HTML is proof/QA only and never the PPTX intermediate.
- PowerPoint is an explicit legacy backend and sampled read-only release certifier.
- Portable mode fails rather than silently dropping a required unsupported capability.
- PowerPoint registry repair remains a manual operator action outside the Skill.
