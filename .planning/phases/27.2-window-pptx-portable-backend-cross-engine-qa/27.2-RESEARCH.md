# Phase 27.2 Research: Portable PPTX Generation and Verification

**Status:** Complete for implementation planning
**Date:** 2026-07-21

## Objective

Choose a portable native-editable PPTX generator and an independent daily verifier, explain the current COM failure precisely, and define a safe architecture that preserves the v5 authority, transaction, and quality contracts.

## Local Evidence

The current repository contains the Phase 22-27.1 COM renderer, backend-bound transaction and candidate-reopen checks, strict RenderPlan, Quality-v2, six calibration fixtures, benchmark harness, and 505-test historical baseline. Direct host diagnostics and a temporary PptxGenJS determinism spike provide the runtime evidence summarized below.

## Local COM Forensics

- Microsoft Office Home 2024, PowerPoint `16.0.20131.20154`, Windows Python 3.13.11, and pywin32 311 are x64.
- PowerPoint application CLSID `{91493441-5A91-11CF-8700-00AA0060263B}` resolves to `POWERPNT.EXE /AUTOMATION`.
- Microsoft PowerPoint TypeLib `{91493440-5A91-11CF-8700-00AA0060263B}` version 2.12 resolves to `MSPPT.OLB`; direct TypeLib load and generated-module creation pass.
- `_Application` IID `{91493442-5A91-11CF-8700-00AA0060263B}` is present in `MSPPT.OLB`, but its Interface registry `TypeLib` points to stale WPS TypeLib `{44720440-94BF-4940-926D-4F38FECF2A48}` version 3.0.
- The registered WPS path points to a missing `C:\Program Files (x86)\WPS Office\12.1.0.16704\office6\wppapi.dll`; WPS is absent from installed-program inventory.
- Early-bound pywin32 therefore fails during `QueryInterface`, while late-bound `IDispatch` starts, reports the expected PowerPoint version, quits, and leaves no process residue.

## Generator Evaluation

### PptxGenJS 4.0.1 — Selected

- Produces native editable text, shapes, images, tables, charts, masters, placeholders, notes, and hyperlinks.
- Runs under the repository's Node 20 environment and has an MIT license.
- Does not implement animation, SmartArt, existing-presentation import, or native PowerPoint grouping. Portable capability negotiation must expose those gaps instead of hiding them.
- Supports object names and alt text, which can carry stable RenderPlan identity metadata for OOXML inspection.
- A deterministic spike produced identical extracted OOXML except for created/modified core timestamps. Normalizing core properties and ZIP metadata can therefore provide byte-level repeatability in the same fingerprinted environment.

### python-pptx — Not Primary

- Strong for Python-native OOXML creation and inspection but has narrower chart and advanced-object behavior than the selected PptxGenJS path.
- Remains useful as reference material; the implementation uses direct ZIP/XML inspection where exact package evidence is required.

### Aspose.Slides — Deferred

- Provides broad headless commercial support and may be a future independent paid verifier or fallback.
- It is not required for Phase 27.2 because the user selected an open-source daily path.

### Marp / Screenshot Slides — Rejected

- Default image-per-slide output does not meet native editability requirements.

## HTML Evaluation

- PptxGenJS's documented HTML feature converts HTML tables rather than arbitrary slide DOM.
- A generic DOM-to-PPTX native compiler would need independent geometry, font, crop, chart, and grouping semantics and would duplicate the governed renderer.
- The repository contains a reference `html2pptx.js` with a restrictive license. It must not be copied, derived, or retained as owned runtime code.
- HTML remains valuable when generated deterministically from RenderPlan as a proof/debug view, because it cannot alter the canonical package.

## Verification Evaluation

### OOXML Semantic Inspection — Required

ZIP/package validity alone cannot prove that generated objects match RenderPlan. The inspector must resolve relationship targets and compare identity, content, media, data, notes, links, masters, and slide geometry to the backend result.

### LibreOffice Impress + Poppler — Selected

- Provides an independent headless open/export path without Microsoft desktop automation.
- It is not a proof of exact PowerPoint rendering; fonts and complex layout may differ.
- It must render a candidate copy with a unique UserInstallation profile and never save the canonical PPTX.
- `pdfinfo` and `pdftoppm` provide page-count, page-size, readability, and PNG evidence.

### PowerPoint — Sampled Certification

- Remains the highest-value compatibility sample because the deliverable will commonly be opened in PowerPoint.
- Certification must be read-only, macro-disabled, process-owned, and unable to modify the canonical file.
- A safe late-bound fallback is allowed only when process ownership can be proven; otherwise certification fails closed.

## Architecture Consequence

```text
FactStore -> BriefPlan -> NarrativePlan -> DeckPlan -> RenderPlan
  -> capability negotiation
  -> PptxGenJS native PPTX
  -> deterministic OOXML normalization
  -> RenderPlan-aware OOXML hard gate
  -> isolated LibreOffice PDF -> Poppler PNG
  -> Quality-v2 / bounded repair / atomic promotion
  -> optional read-only PowerPoint sampled certification
```

## Options

| Option | Result |
|---|---|
| Keep COM as daily renderer | Rejected: current host registration is unreliable and unattended desktop automation remains a daily dependency |
| PptxGenJS + OOXML + LibreOffice | Selected: native editable OOXML, deterministic control, and independent headless proof |
| Arbitrary HTML-to-PPTX | Rejected: loses editability when rasterized or duplicates a full native renderer when object-mapped |
| Aspose.Slides | Deferred paid fallback POC |
| Marp/image slides | Rejected for client-editable delivery |

## Recommendation

Implement direct RenderPlan-to-PptxGenJS generation, deterministic OOXML normalization and semantic inspection, isolated LibreOffice/Poppler proof rendering, Quality-v2 hard gates, and optional read-only PowerPoint sampling. Keep HTML as a parallel proof view only.

## Assumptions To Confirm

- None. The user selected PptxGenJS, WSL LibreOffice, proof-only HTML, and sampled PowerPoint certification. Runtime versions must be discovered and fingerprinted during implementation rather than assumed.
