# Phase 27.2 Context: Portable Backend and Cross-Engine QA

## Canonical Data Flow

- FactStore, BriefPlan, NarrativePlan, DeckPlan v1, and RenderPlan remain authoritative and backend-neutral.
- Models may select registered semantic intent but may not emit PptxGenJS code, OOXML, HTML/CSS, COM, or coordinates.
- PptxGenJS consumes RenderPlan directly; HTML is a parallel proof projection, never an input to the PPTX generator.

## Implementation Decisions

- `--backend auto|pptxgenjs|com`; `auto` selects PptxGenJS for governed generation.
- `--verification portable|powerpoint`; `portable` is the default and `powerpoint` always includes portable gates first.
- Macro-enabled output, physical template import, required motion, SmartArt, and native grouping remain explicit COM-only capabilities.
- Portable diagrams use native editable children with logical-group identity metadata.
- PowerPoint certification is read-only and may be `NOT_RUN` without invalidating a Phase 27.2 portable PASS.

## Dependencies

- Pin `pptxgenjs@4.0.1` in the repository lockfile.
- Install WSL `libreoffice-impress`; record the actual package and runtime version.
- Use available `pdfinfo` and `pdftoppm`; record the Poppler version.
- Fingerprint Node, npm, OS, locale, fonts, PptxGenJS, LibreOffice, Poppler, registries, schemas, Skill, assets, and optional PowerPoint.

## Existing Patterns To Preserve

- Strict schemas and `additionalProperties: false` for model-controlled objects.
- Registry binding, deterministic tie-breaks, safe margins, theme tokens, asset provenance, crop-not-stretch, and native chart/table/diagram semantics.
- Candidate-only mutation, exact source hashes, package validation, bounded pre/post repair, rollback, atomic artifacts, and no placeholder promotion.
- Existing COM renderer, recording fake-COM tests, macro-security restoration, source formats, and legacy report readers.

## Allowed Scope

- `skills/owned/window-pptx`, its schemas, references, registries, Node worker, Python runner/backend/QA modules, tests, repository package metadata, and Phase 27.2 evidence.
- WSL LibreOffice package installation selected by the user.
- Read-only PowerPoint and registry diagnosis under existing ownership rules.

## Forbidden Scope

- Root user DeckPlan files, unmanaged user files, secrets, CLI global configuration, copied Huashu/restricted runtime code, source-deck overwrite, automatic registry repair, broad process termination, or arbitrary macros/plugins.

## Integration And Compatibility

- Existing direct DeckPlan and COM renderer routes remain available, but governed `auto` uses PptxGenJS and never falls back to COM implicitly.
- Existing Quality-v1/v2 and report readers remain compatible; new backend, verification, and fingerprint fields are additive and versioned.
- Portable verification precedes optional PowerPoint verification and owns the canonical output.
- Phase 28 consumes only clean post-27.2 fingerprints; Phase 29 adds sampled certification without rewriting artifacts.

## Failure Semantics

- Capability mismatch: fail before candidate creation.
- PptxGenJS/Node failure: retain structured backend diagnostics; do not invoke COM automatically.
- OOXML semantic failure: retain candidate and report in evidence staging; do not promote.
- LibreOffice/Poppler failure: retain diagnostics and fail portable verification; do not resave the candidate.
- Quality-v2 failure: apply only the existing bounded monotonic repair contract, then fail closed if unresolved.
- PowerPoint certification failure: preserve the portable artifact and mark certification FAIL/NOT_RUN; never modify or delete the portable deliverable.

## Downstream Gates

- Phase 28 cannot refreeze or aggregate until a clean post-27.2 fingerprint exists.
- Existing benchmark manifests are pre-27.2/noncanonical.
- Phase 29 certifies a frozen 10% sample plus every high-risk capability sample in PowerPoint and runs the final post-implementation OpenCode audit.
